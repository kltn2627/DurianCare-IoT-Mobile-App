# Physical-iPhone E2E parity checklist

This checklist is evidence-driven. Every row starts as `NOT TESTED`; change it to `PASS`, `FAIL`, or `BLOCKED` only after recording the runtime evidence in **Notes**. A successful TypeScript build is not E2E evidence.

## Test setup and capture rules

- Use a physical iPhone and the Web client on the same LAN. `EXPO_PUBLIC_API_BASE_URL` must be a LAN-reachable Gateway URL, never `localhost` or `127.0.0.1`.
- Capture the role, user ID (or a safe test-account label), entity IDs, timestamp, request status, and a screenshot/video for every failed or blocked row. Never put a JWT, password, refresh token, or private message content in this document or logs.
- Seed one disposable farm, zone, season, plan, activity, IoT device with telemetry, public community post with an image, and a single durian-leaf photo. Do not use mocks.
- For a bidirectional row, complete the Mobile mutation, verify it in Web after refresh, then perform the equivalent Web mutation and refresh Mobile.
- Existing DEV signals: `[DurianCare network]`, `[Diagnosis]`, `[DurianCare AI diagnosis]`, and `[MOBILE_MEDIA]`. For a failed image, capture `feature`, `originalUrl`, `resolvedUrl`, `httpStatus`, `contentType`, `requiresAuth`, and `classification`. Native image loading cannot reliably expose HTTP status/content type, so those may be `undefined`; do not infer an HTTP failure from that alone.
- The diagnosis test must retain its existing timing logs. Record the resolved URL, upload progress, response status, and the backend `PREDICTION_TRACE` / `AI_PROFILE` for the same file before treating a performance difference as a mobile issue.

## Recommended physical-iPhone execution order

1. Confirm LAN Gateway reachability, authenticate each test account, and capture the effective API base URL without credentials.
2. Run `FZS-01` through `FZS-04`, then `CUL-01` through `CUL-03`, always doing the Web refresh immediately after a mutation.
3. Run `AI-01` through `AI-03` with the one fixed leaf image and preserve timing evidence before any performance change is proposed.
4. Run `MED-01` through `MED-05`; record `[MOBILE_MEDIA]` only for failures. Leave `B1` blocked.
5. Run IoT rows only against real telemetry/alerts, then authorization rows with the role matrix.
6. Use both clients for community and chat rows, including the Socket.IO reconnect test.
7. Finish with notification inbox/deep-link checks, then the separate real-push foreground/background/cold-start run, and profile/avatar persistence.

## Completion evidence

For a `PASS`, Notes must contain the test identity, entity ID(s), timestamp, HTTP/socket evidence, and Web cross-check observation. For a `FAIL`, state the first boundary that disagreed (Mobile UI, request, Gateway, service response, media rendering, or Web). For `BLOCKED`, name the missing server contract or infrastructure and retain the captured evidence.
